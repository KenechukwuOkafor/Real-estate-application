# ADR-012 — Adopt Cursor-Based Pagination as the Default Pagination Strategy

## Status

Accepted

---

# Context

Ruvo exposes numerous collections including:

- Listings
- Messages
- Notifications
- Reports
- Audit logs
- Search results
- Inspection requests

These collections are expected to grow continuously.

Traditional offset pagination becomes increasingly inefficient as datasets expand because the database must scan and discard earlier rows before returning results.

This leads to slower queries and inconsistent pagination when records are inserted or deleted between requests.

---

# Decision

Cursor-based pagination will be the default pagination strategy across all APIs.

Offset pagination is prohibited for production endpoints unless explicitly justified by a future ADR.

---

# Cursor Structure

Cursors reference the last visible record rather than a page number.

Example:

```
GET /listings?after=cursor
```

instead of

```
GET /listings?page=12
```

The cursor is treated as an opaque value by clients.

Clients must not rely on its internal structure.

---

# Rationale

## Performance

Cursor pagination scales consistently regardless of dataset size.

---

## Consistency

Users do not experience duplicate or skipped records when new data is inserted.

---

## Infinite Scrolling

Cursor pagination aligns naturally with mobile-first infinite scrolling.

---

## Database Efficiency

Indexed cursor lookups avoid expensive offset scans.

---

## API Stability

Opaque cursors allow implementation changes without breaking clients.

---

# Alternatives Considered

## Offset Pagination

Pros

- Familiar.
- Easy to understand.

Cons

- Poor scalability.
- Inconsistent results.
- Expensive database scans.

Decision:

Rejected.

---

## Page Number Pagination

Pros

- Simple UI.

Cons

- Unsuitable for rapidly changing datasets.

Decision:

Rejected.

---

# Consequences

## Positive

- Better scalability
- Better performance
- Stable pagination
- Mobile-friendly API design

## Negative

- Slightly more complex implementation.
- Clients cannot jump directly to arbitrary pages.

---

# Non-Negotiable Constraints

- Public APIs use cursor pagination.
- Cursors remain opaque.
- Cursor generation is deterministic.
- APIs document pagination behavior consistently.

---

# Decision Impact Assessment

## Product Impact

Improves responsiveness and creates a smoother browsing experience for users.

## Engineering Impact

Encourages scalable API design from the beginning.

## Operational Impact

Reduces database load as the platform grows.

## Risk Assessment

Risks

- Incorrect cursor generation.
- Duplicate results.

Mitigations

- Stable ordering.
- Comprehensive pagination tests.
- Indexed sort columns.

# AI Implementation Guidance

Always prefer cursor pagination for collection endpoints.

Avoid offset-based queries unless specifically approved.

Ensure deterministic ordering before generating cursors.

## Definition of Done

Collection endpoints return opaque cursors, maintain stable ordering, and perform efficiently regardless of dataset size.
