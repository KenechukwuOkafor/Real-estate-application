# ADR-013 — Adopt a Unified Search Architecture

## Status

Accepted

---

# Context

Search is the primary entry point into the Ruvo marketplace.

Users do not think in terms of database filters.

Instead they naturally express their intent.

Examples:

- "2 bedroom apartment in Nsukka under ₦800,000"
- "Verified apartments near UNN"
- "Self-contained with borehole"
- "3 bedroom duplex in Enugu"

The architecture must support a search experience that feels like a single intelligent system rather than dozens of independent filters.

---

# Decision

Ruvo will expose a **Unified Search Architecture**.

Search requests are interpreted as a single search intent.

The backend is responsible for combining:

- Keyword matching
- Structured filters
- Geographic filtering
- Verification status
- Availability
- Property attributes
- Ranking

into one coherent result.

The client does not construct SQL-like queries.

---

# Search Inputs

A search request may include:

- Free text
- Location
- Price range
- Property type
- Bedrooms
- Bathrooms
- Amenities
- Verification
- Availability
- Sorting

These inputs are combined into a single search operation.

---

# Ranking Principles

Results should prioritize:

1. Exact location matches
2. Verification status
3. Availability
4. Keyword relevance
5. Listing quality
6. Freshness
7. User-selected sorting

Ranking algorithms may evolve without changing the public API.

---

# Search Responsibilities

Search is responsible for:

- Query parsing
- Filter composition
- Ranking
- Pagination
- Suggestions
- Empty-state recommendations

Search is not responsible for business authorization.

Authorization remains enforced separately.

---

# Rationale

## Natural User Experience

Users should search naturally rather than learning system-specific syntax.

---

## Separation of Concerns

Clients describe intent.

Servers determine implementation.

---

## Scalability

The architecture allows future enhancements including:

- Semantic search
- AI-assisted search
- Personalized ranking
- Geospatial ranking

without changing client APIs.

---

# Alternatives Considered

## Independent Filter APIs

Pros

- Simple implementation.

Cons

- Poor UX.
- Difficult to extend.

Decision:

Rejected.

---

## Client-side Search Composition

Pros

- Flexible.

Cons

- Large payloads.
- Inconsistent behavior.
- Security concerns.

Decision:

Rejected.

---

# Consequences

## Positive

- Better user experience.
- Cleaner APIs.
- Centralized ranking.
- Future-proof search.

## Negative

- Increased backend complexity.
- Ranking requires continuous tuning.

---

# Non-Negotiable Constraints

- Search behaves as one unified capability.
- Ranking logic remains server-side.
- Clients submit intent rather than implementation.
- Authorization is enforced independently.

---

# Decision Impact Assessment

## Product Impact

Creates a modern search experience aligned with user expectations.

## Engineering Impact

Centralizes search logic and simplifies client applications.

## Operational Impact

Search improvements can be deployed without client updates.

# AI Implementation Guidance

Treat search as an orchestration layer rather than a collection of unrelated filters.

Ranking must remain deterministic and measurable.

## Definition of Done

Users can express search intent naturally while receiving fast, relevant, and consistently ranked results through a single search interface.
