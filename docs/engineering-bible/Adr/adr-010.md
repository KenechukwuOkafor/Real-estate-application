# ADR-010 — Adopt Row Level Security as a First-Class Authorization Layer

## Status

Accepted — **amended by ADR-010-A1**.

> **Amendment 1 (ADR-010-A1) applies to this decision.**
>
> Implementation established that policies alone do not constitute the
> authorization boundary at the database. Privilege grants are part of it.
>
> Two facts this ADR did not account for, both found during migration rather
> than review, and both live at the time:
>
> - Owning a row does not bound what may be changed within it. An agent owns
>   their listing row, and that row contains the column determining whether the
>   listing is published. The row predicate is satisfied and the write must
>   still be refused — which a grant does, and a policy does not.
> - Default privileges were broader than any policy. Anonymous and
>   authenticated roles held `SELECT`, `INSERT`, `UPDATE`, `DELETE` and
>   `TRUNCATE` on every table, so RLS was operating as the *only* boundary
>   rather than the *final* one, inverting this ADR's intent.
>
> Read ADR-010-A1 alongside this document. Enabling RLS on a table without
> first reviewing its grants does not satisfy ADR-010.

---

# Context

Authentication identifies users.

Authorization determines what those users may access.

Many systems rely entirely on API logic for authorization.

This creates a single point of failure.

A programming mistake may unintentionally expose sensitive data.

Ruvo requires authorization to be enforced at multiple layers.

---

# Decision

Row Level Security (RLS) within PostgreSQL will serve as the final authorization boundary.

Even if an API contains defects, the database must continue enforcing ownership and access policies.

# Why RLS?

## Defense in Depth

Security should never rely on one layer.

Every request is validated independently.

---

## Data Ownership

Examples:

Users only read their own messages.

Agents edit only their own listings.

Customers view only their own inspections.

Administrators receive elevated permissions through explicit policies.

---

## Reduced Human Error

Database policies continue protecting data even when application bugs occur.

---

## Consistency

Every service accessing PostgreSQL follows identical authorization rules.

---

# Alternatives Considered

## API Only Authorization

Pros

Simple.

Cons

Decision:

Rejected.

---

## Application Middleware Only

Pros

Centralized.

Cons

Bypass possible.

Decision:

Rejected.

# Consequences

## Positive

- Stronger security
- Consistent authorization
- Better auditability

## Negative

- Additional policy management.
- Requires PostgreSQL expertise.

---

# Non-Negotiable Constraints

- Protected tables require RLS.
- Policies are version controlled.
- Anonymous access is explicitly defined.
- Service-role credentials remain restricted.

Never disable policies for convenience.
