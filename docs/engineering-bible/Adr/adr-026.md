# ADR-026 — Adopt Sentry as the Centralized Error Monitoring Platform

## Status

Accepted

---

# Context

Production software inevitably encounters failures.

Without centralized monitoring, engineering teams depend upon:

- User reports
- Server logs
- Manual debugging

This delays incident detection and increases recovery time.

Ruvo requires proactive visibility into application failures across both frontend and backend systems.

---

# Decision

Ruvo will use **Sentry** as the centralized platform for application error monitoring and performance observability.

Every production service integrates with Sentry.

Errors are reported automatically rather than waiting for user feedback.

---

# Monitoring Scope

Sentry monitors:

- Frontend exceptions
- API failures
- Server-side errors
- Background job failures
- Performance bottlenecks
- Release health

Critical alerts are routed to the engineering team.

---

# Error Context

Captured events should include:

- Request ID
- User ID (when appropriate)
- Session ID
- Release version
- Environment
- Stack trace
- Breadcrumbs
- Device information

Sensitive personal information must never be transmitted.

---

# Alert Strategy

Alerts are classified by severity.

Examples:

- Critical
- High
- Medium
- Low

Alert routing follows predefined operational procedures.

---

# Rationale

## Faster Incident Detection

Errors are detected immediately rather than through customer complaints.

---

## Improved Debugging

Rich diagnostic information significantly reduces investigation time.

---

## Release Confidence

Errors can be correlated with specific deployments.

---

## Operational Visibility

Engineering gains continuous insight into production health.

---

# Alternatives Considered

## Server Logs Only

### Pros

- Minimal tooling.

### Cons

- Poor discoverability.
- Difficult correlation.
- Reactive operations.

Decision:

Rejected.

---

## Custom Monitoring Platform

### Pros

- Full customization.

### Cons

- High engineering cost.
- Long maintenance burden.

Decision:

Rejected.

---

# Consequences

## Positive

- Faster incident response.
- Better debugging.
- Improved release quality.
- Stronger operational awareness.

## Negative

- Additional external dependency.
- Alert configuration requires ongoing tuning.

---

# Non-Negotiable Constraints

- Every production service integrates with Sentry.
- Sensitive data is sanitized before transmission.
- Release versions accompany every event.
- Monitoring remains enabled across all production environments.

---

# Decision Impact Assessment

## Product Impact

Improves platform stability and reduces customer-facing incidents.

## Engineering Impact

Provides consistent production observability across services.

## Operational Impact

Supports proactive monitoring and structured incident response.

# AI Implementation Guidance

Ensure all production services emit structured errors.

Never suppress exceptions silently.

Include sufficient context for debugging while excluding sensitive information.

## Definition of Done

Production services automatically report actionable errors, correlate failures with releases, and support rapid incident investigation.
