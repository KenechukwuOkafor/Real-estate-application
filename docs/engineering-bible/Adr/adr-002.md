# ADR-002 — Adopt Supabase as the Primary Backend Platform

## Status

**Accepted**

---

# Context

Ruvo requires a backend platform that can support a modern marketplace without introducing unnecessary operational complexity during the MVP stage.

The backend must support:

- PostgreSQL as the primary database.
- Row Level Security (RLS).
- Secure object storage for images and videos.
- Authentication integration with Clerk.
- Real-time capabilities where appropriate.
- SQL-first development.
- Database migrations.
- Scalability from the first city (Nsukka) to nationwide deployment.

The team also wants to minimize infrastructure management during the early stages of the company so engineering effort is spent building product features rather than maintaining servers.

---

# Decision

Ruvo will adopt **Supabase** as its backend platform.

Supabase will provide:

- PostgreSQL database
- Storage buckets
- Row Level Security
- SQL migrations
- Edge Functions (when appropriate)
- Database backups
- Realtime services (only where justified)

Authentication will remain the responsibility of **Clerk**. Supabase Authentication will not be used.

---

# Rationale

## 1. PostgreSQL First

PostgreSQL is one of the most mature relational databases available.

It provides:

- ACID compliance
- Rich indexing
- Full-text search
- JSON support
- Geospatial extensions (PostGIS if needed)
- Excellent performance

Because the Ruvo domain contains highly relational data (users, agents, listings, inspections, subscriptions, moderation, reports), PostgreSQL is a natural fit.

---

## 2. Row Level Security

Security should not depend solely on API logic.

Supabase allows authorization rules to be enforced directly at the database layer through RLS.

This provides defense in depth.

---

## 3. Storage Integration

Property listings require:

- Images
- Videos
- Verification documents

Supabase Storage provides a unified solution integrated with the same backend platform.

---

## 4. Developer Productivity

Supabase reduces infrastructure overhead by providing:

- Managed PostgreSQL
- SQL migrations
- Dashboard tooling
- Local development support
- Backup capabilities

This allows the team to focus on product development.

---

## 5. Scalability

Supabase supports the expected growth path:

- MVP in Nsukka
- Expansion to Enugu
- Expansion across Nigeria

without requiring a backend platform migration.

---

# Alternatives Considered

## Firebase

### Pros

- Excellent real-time capabilities.
- Mature ecosystem.
- Easy onboarding.

### Cons

- No PostgreSQL.
- Firestore's document model is less suitable for Ruvo's relational domain.
- More difficult to express complex marketplace relationships.
- SQL expertise becomes less reusable.

**Decision:** Rejected.

---

## Self-hosted PostgreSQL

### Pros

- Maximum control.
- Lower long-term infrastructure costs.

### Cons

- Higher operational burden.
- Requires database administration from day one.
- Slower MVP delivery.

**Decision:** Rejected for MVP.

---

## PocketBase

### Pros

- Lightweight.
- Simple deployment.

### Cons

- Smaller ecosystem.
- Limited maturity.
- Less suitable for long-term marketplace growth.

**Decision:** Rejected.

---

# Consequences

## Positive

- Mature relational database.
- Built-in storage.
- Strong security model.
- SQL-first architecture.
- Reduced operational complexity.
- Excellent compatibility with Next.js.

## Negative

- Vendor-specific features should be used carefully.
- Some advanced scaling options depend on Supabase's platform roadmap.
- Engineers must understand PostgreSQL and RLS.

---

# Non-Negotiable Constraints

- PostgreSQL is the canonical database.
- Business rules must not rely solely on frontend validation.
- RLS policies are mandatory for protected data.
- Clerk remains the identity provider.
- Database migrations are version-controlled.

---

# Future Considerations

Potential future enhancements include:

- Read replicas.
- PostGIS for advanced geospatial search.
- Queue-based background processing.
- Dedicated analytics database.
- Data warehouse integration.

These should only be introduced when operational metrics justify the additional complexity.

# AI Implementation Guidance

## Context

Supabase is the approved backend platform for Ruvo.

All database, storage, and authorization decisions should assume Supabase unless superseded by a future ADR.

## Non-Negotiable Rules

- Use PostgreSQL as the source of truth.
- Implement authorization with RLS.
- Store media in Supabase Storage.
- Keep authentication delegated to Clerk.
- Manage schema changes through migrations.

## Common Mistakes

- Implementing business rules only in the frontend.
- Bypassing RLS with privileged database access.
- Treating Supabase as a NoSQL backend.
- Duplicating authentication logic already handled by Clerk.

## Definition of Done

Backend implementations conform to the Supabase architecture, enforce RLS where appropriate, and remain consistent with the documented database model.
