# ADR-003 — Adopt Clerk as the Primary Identity Provider

## Status

**Accepted**

---

# Context

Ruvo requires a secure, scalable, and developer-friendly identity management solution that supports both public users and verified agents while minimizing the complexity of authentication infrastructure.

Authentication is a foundational capability upon which every protected feature depends, including:

- User registration
- User login
- Session management
- Protected routes
- Role assignment
- Agent onboarding
- Admin access
- Subscription ownership
- Inspection requests
- Messaging
- Audit logging

Identity must be separated from business data. Authentication answers **"Who is this user?"** while Ruvo's database answers **"What can this user do?"**

---

# Decision

Ruvo will use **Clerk** as the exclusive identity provider.

Clerk is responsible for:

- User registration
- User login
- Password management
- Email verification
- Session management
- OAuth providers (future)
- Multi-factor authentication (future)
- Authentication tokens

Supabase Authentication will **not** be used.

Application-specific user information (roles, profiles, verification status, subscriptions, etc.) will be stored in PostgreSQL.

---

# Architectural Responsibilities

## Clerk owns

- Authentication
- Identity
- Sessions
- Credentials
- Email verification
- Password reset

---

## Ruvo owns

- User profiles
- Roles
- Permissions
- Verification status
- Agent information
- Listings
- Payments
- Subscriptions
- Business rules

Identity is therefore isolated from application state.

---

# Rationale

## 1. Separation of Concerns

Authentication should never become mixed with marketplace logic.

Keeping identity external allows Ruvo to evolve independently without rewriting authentication infrastructure.

---

## 2. Security

Clerk provides professionally managed authentication including:

- Secure session management
- Password hashing
- Device handling
- Cookie security
- Authentication best practices

This significantly reduces security risk.

---

## 3. Integration

Clerk integrates cleanly with:

- Next.js App Router
- Server Components
- Middleware
- Supabase
- TypeScript

No custom authentication system is required.

---

## 4. Scalability

Identity remains consistent as Ruvo expands from:

Nsukka

↓

Enugu

↓

Nigeria

↓

Future international markets

No architectural changes are required.

---

## 5. Maintainability

Authentication bugs are among the highest-risk software failures.

Delegating authentication allows the engineering team to focus on marketplace functionality.

---

# Authentication Flow

The authentication lifecycle follows this sequence:

1. User signs up through Clerk.
2. Clerk creates the identity.
3. Clerk returns the authenticated user ID.
4. Ruvo synchronizes the user into PostgreSQL.
5. A profile record is created if one does not already exist.
6. Roles are assigned according to onboarding.
7. Business permissions are enforced using PostgreSQL and RLS.

Authentication and authorization remain separate concerns.

---

# Alternatives Considered

## Supabase Authentication

### Pros

- Native integration
- Simpler initial setup

### Cons

- Couples authentication to the database platform.
- Less flexibility if backend architecture evolves.
- Duplicate responsibility with Clerk.

**Decision:** Rejected.

---

## Auth.js (NextAuth)

### Pros

- Open source
- Highly customizable

### Cons

- Greater implementation and maintenance burden.
- Authentication security becomes the application's responsibility.

**Decision:** Rejected.

---

## Custom Authentication

### Pros

- Maximum control

### Cons

- Extremely high security risk.
- Ongoing maintenance burden.
- Reinvents solved problems.

**Decision:** Strongly Rejected.

---

# Consequences

## Positive

- Enterprise-grade authentication.
- Reduced security burden.
- Better developer productivity.
- Cleaner architecture.
- Identity separated from business logic.

---

## Negative

- Dependency on a third-party identity provider.
- Vendor-specific APIs require familiarity.
- Internet connectivity is required for authentication.

---

# Non-Negotiable Constraints

- Clerk is the only authentication provider.
- Supabase Authentication remains disabled.
- Passwords are never stored by Ruvo.
- Roles are never stored in Clerk metadata.
- Authorization decisions always occur inside Ruvo.

---

# Future Considerations

Potential future enhancements include:

- Google OAuth
- Apple Sign-In
- Multi-factor authentication
- Passkeys
- Organization accounts
- Enterprise SSO

These enhancements must integrate through Clerk rather than replacing it.

# AI Implementation Guidance

## Context

This ADR establishes Clerk as the canonical identity provider.

AI coding agents must assume all authentication flows originate from Clerk and that PostgreSQL stores only application-specific user data.

## Non-Negotiable Rules

- Never implement custom authentication.
- Never store passwords.
- Never duplicate authentication logic.
- Keep identity separate from authorization.
- Sync authenticated users into PostgreSQL before business operations.

## Common Mistakes

- Mixing authentication with user profiles.
- Storing business roles inside Clerk metadata.
- Trusting client-side authentication state without server verification.
- Using Supabase Authentication alongside Clerk.

## Definition of Done

Authentication flows use Clerk exclusively, user records are synchronized into PostgreSQL, and authorization remains enforced by Ruvo's backend and database policies.
