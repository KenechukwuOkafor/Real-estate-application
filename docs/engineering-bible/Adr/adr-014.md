# ADR-014 — Treat Media as a First-Class Domain

## Status

Accepted

> **Extended by ADR-033.**
>
> ADR-014 establishes media as a domain entity with its own UUID and metadata.
> ADR-033 adds how that entity is stored and served: privately, through
> short-lived signed URLs, with opaque generated paths.
>
> The two are complementary — this ADR says media is not an attachment,
> ADR-033 says it is not a public file either.

---

# Context

Media is fundamental to a real estate marketplace.

High-quality property images and videos directly influence:

- User trust
- Listing quality
- Engagement
- Conversion

Many systems treat media as simple file attachments.

This limits extensibility and prevents the platform from managing media throughout its lifecycle.

---

# Decision

Ruvo will model media as an independent business domain.

Images and videos are not attachments.

They are domain entities with their own lifecycle, metadata, processing pipeline, and business rules.

Listings reference media rather than containing media.

---

# Media Responsibilities

The Media domain owns:

- Uploads
- Metadata
- Processing
- Compression
- Thumbnails
- Storage
- Ordering
- Lifecycle
- Visibility
- Access URLs

---

# Media Metadata

Every media asset maintains metadata including:

- UUID
- Owner
- Listing
- Type
- MIME type
- Resolution
- Dimensions
- Duration (video)
- File size
- Processing status
- Created timestamp

---

# Media Lifecycle

Media progresses through defined states:

Pending Upload

↓

Uploaded

↓

Processing

↓

Optimized

↓

Published

↓

Archived

↓

Deleted

Lifecycle transitions are managed independently of listing publication.

---

# Rationale

## Separation of Concerns

Listings describe properties.

Media describes visual assets.

Each domain evolves independently.

---

## Scalability

Future capabilities such as:

- AI image analysis
- Automatic tagging
- Duplicate detection
- Watermarking
- Content moderation

can be added without redesigning Listings.

---

## Reusability

Media services become reusable across future product areas.

---

## Operational Simplicity

Dedicated processing pipelines become easier to manage and monitor.

---

# Alternatives Considered

## Store Files Inside Listings

Pros

- Simple schema.

Cons

- Tight coupling.
- Difficult scaling.
- Poor extensibility.

Decision:

Rejected.

---

## External Attachment Model

Pros

- Familiar.

Cons

- Weak lifecycle management.
- Limited metadata support.

Decision:

Rejected.

---

# Consequences

## Positive

- Independent scalability.
- Cleaner architecture.
- Better processing.
- Easier future AI integration.

## Negative

- Additional domain complexity.
- More database relationships.

---

# Non-Negotiable Constraints

- Every media asset has its own UUID.
- Listings reference media.
- Processing occurs asynchronously.
- Metadata is preserved independently of storage.

---

# Decision Impact Assessment

## Product Impact

Improves listing quality and supports richer user experiences.

## Engineering Impact

Creates a modular and extensible media platform.

## Operational Impact

Enables dedicated monitoring, processing, and optimization pipelines.

# AI Implementation Guidance

Treat media as business entities, not file uploads.

Processing pipelines must be independent of listing logic.

Avoid embedding media-specific logic inside the Listings domain.

## Definition of Done

Media exists as an independent domain with its own lifecycle, metadata, processing pipeline, and relationships to listings.
