# ADR-031 — Adopt a First-Class Geospatial Model with Graduated Location Precision

## Status

Proposed

---

# Context

Ruvo's geographic model is currently hierarchical only:

```
Country → State → City → Area → Listing
```

A listing knows which area it belongs to. It does not know where it is.

This is sufficient for the launch city. Nsukka is compact and campus-centric, and area
names carry most of the meaning a seeker needs. It is not sufficient for what follows.

Several planned and likely capabilities require coordinates:

- Radius and "near me" search
- Distance to campus, market, or transit
- Map bounding-box queries
- Marker clustering
- Area boundaries rather than area labels
- Proximity ranking
- Geographic analytics for expansion decisions

None of these can be added retroactively without cost. Coordinates cannot be inferred
from existing rows: Nigerian informal-area addressing is landmark-based rather than
street-based, so listings cannot be geocoded from their stored text. Backfilling means
asking agents to revisit properties they listed months earlier, and most will not.

A second problem is specific to Ruvo's trust model. A listing's exact location is
valuable to a committed seeker and hazardous when published openly. Publishing precise
coordinates on an open listing page exposes properties — frequently occupied ones — to
anyone browsing. It also removes the agent's role from the transaction, which weakens
the incentive to participate in the marketplace at all.

Finally, coordinate accuracy depends on the agent placing the pin. Ruvo exists because
agent claims cannot be assumed accurate. An incorrect pin rendered confidently on a map
is worse than no pin, because it presents as verified information.

---

# Decision

Ruvo adopts a first-class geospatial model at the data layer immediately, and defers
map-based discovery in the user interface.

Specifically:

1. **PostGIS is enabled** on the primary database. Coordinates are stored as
   `geography(Point, 4326)`, not as two decimal columns.
2. **Listings capture an exact location at creation time.** Agent pin placement is part
   of the listing form and is required before submission for review.
3. **Areas become geographic entities.** An area has a representative point and, where
   practical, a boundary polygon — not only a name.
4. **Location precision is graduated.** Exact coordinates are private. Public surfaces
   receive a deterministic approximate point.
5. **Pin plausibility is part of moderation.** A listing whose pin falls outside its
   declared area is rejected in review.
6. **Map-based discovery UI is out of scope for the launch city** and requires a
   superseding decision before implementation.

---

# Graduated Location Precision

Every listing carries two location values:

| Value | Storage | Visibility |
|---|---|---|
| Exact point | `geography(Point, 4326)` | Private. Never leaves the database unmasked. |
| Approximate point | Derived, deterministic | Public from the moment the listing is published. |

## Derivation

The approximate point is a fixed deterministic offset from the exact point, seeded by
the listing identifier, constrained to a radius of **250 metres**.

Deterministic rather than random, because a value that changes between requests reveals
the true centre through repeated sampling.

## Disclosure

Exact location is disclosed when an inspection request reaches **Accepted**.

That event is the point at which both parties have committed: the seeker has expressed
genuine intent and the agent has agreed to meet. It is also already a state transition
in the Inspection domain, so no new mechanism is required.

Disclosure is enforced at the database through RLS, not in application code, consistent
with ADR-010. An API bug must not be able to leak an exact coordinate.

---

# Scope of Map UI

Map-based discovery is deliberately excluded from the launch city.

## Reasoning

- Nsukka's student housing sits within a few kilometres of the university. Geography is
  not the difficult part of the decision for a seeker; price and legitimacy are.
- Pin accuracy is unverified until moderation covers it, and an inaccurate map is a
  trust liability rather than a trust feature.
- Map tile requests carry a per-load cost to the platform and a data cost to the user.
  Both matter on a page opened many times per session over mobile data.

## What triggers reconsideration

Map discovery should be revisited when any of the following hold:

- The platform operates in a city where areas are not walkable from one another.
- Listing density within a single area exceeds roughly one hundred active listings.
- Pin accuracy is verified as part of the moderation workflow with measured error rates.

This ADR does not need superseding to build the map. It needs superseding to change the
data model. The map is a UI decision that this model already supports.

---

# Rationale

## The cost asymmetry is decisive

Enabling PostGIS and capturing a point at creation is close to free today. Acquiring
coordinates for historical listings later is expensive, manual, and incomplete. When one
direction is cheap and the other is not, the cheap one should happen first even if the
capability is unused for a year.

## Deferring the UI does not defer the model

The common failure is to treat "we are not building maps yet" as licence to skip the
geographic model. The two decisions are independent. This ADR takes the safe side of
each.

## Privacy is a product feature, not a compliance chore

Graduated precision protects occupied properties, preserves the agent's role in the
transaction, and gives the seeker a concrete reason that requesting an inspection is
worth doing. It reinforces the conversion event rather than obstructing it.

# Alternatives Considered

## Two decimal columns, no PostGIS

### Pros

- No extension dependency.
- Adequate for bounding-box queries.

### Cons

- Distance calculations must be hand-written and are error-prone across latitudes.
- No spatial indexing, so proximity queries degrade with volume.
- Polygon containment for area boundaries is impractical.
- Migrating to PostGIS later requires rewriting every query that touches location.

Decision: Rejected. The extension is available in Supabase at negligible cost.

---

## Defer coordinates entirely until maps are built

### Pros

- Less work now.
- No unused columns.

### Cons

- Backfill is manual, agent-dependent, and will be incomplete.
- Area boundaries remain unavailable, blocking area-based expansion analysis.

Decision: Rejected. This is the failure mode the ADR exists to prevent.

---

## Publish exact coordinates

### Pros

- Simpler. No derivation, no disclosure rules.

### Cons

- Exposes occupied properties to open browsing.
- Removes the agent from the transaction, weakening supply-side participation.
- Irreversible: a published coordinate cannot be recalled.

Decision: Rejected.

---

## Random rather than deterministic offset

### Pros

- Marginally simpler to implement.

### Cons

- Repeated requests average out to the true location.

Decision: Rejected.

---

# Consequences

## Positive

- Geographic capability becomes available without a migration.
- Area entities gain boundaries, supporting expansion analysis.
- Location privacy is enforced at the database rather than trusted to application code.
- Exact location becomes a concrete reason to request an inspection.

## Negative

- PostGIS is an additional extension to operate and keep current.
- Agents must place a pin, adding a step to listing creation.
- Moderation gains a plausibility check, adding load to a manual queue.
- Coordinate columns remain unused by product surfaces for some time.

---

# Non-Negotiable Constraints

- Coordinates are stored as PostGIS geography types, never as loose decimal columns.
- Exact coordinates are never returned by a public endpoint.
- The approximate point is deterministic for a given listing.
- Precision disclosure is enforced by RLS, not application logic.
- Every published listing has a location. Listings without one cannot be approved.
- Introducing map-based discovery does not require superseding this ADR. Changing the
  storage model or the disclosure rule does.

---

# Decision Impact Assessment

## Product Impact

Preserves future geographic capability without shipping a map that current listing
density cannot justify. Strengthens the inspection conversion event by attaching a
concrete disclosure to it.

## Engineering Impact

Adds an extension, a migration, a pin control in the listing form, and RLS policies
governing coordinate visibility. Constrains all future location work to a single model.

## Operational Impact

Adds a pin plausibility check to listing moderation. Increases per-listing review time.

## Risk Assessment

### Risks

- Agents place pins carelessly, degrading data quality before anyone notices.
- The 250 metre radius proves wrong for dense areas.
- Pin capture adds friction to listing creation and reduces agent completion rates.

### Mitigations

- Moderation rejects pins falling outside the declared area.
- The offset radius is configuration, not a constant embedded in queries.
- Pin placement defaults to the area's representative point, so the agent adjusts rather
  than starting from an empty map.

# AI Implementation Guidance

## Context

Ruvo stores geographic data using PostGIS. Location has two precisions: exact, which is
private, and approximate, which is public.

## Non-Negotiable Rules

- Use PostGIS geography types. Never introduce `latitude` and `longitude` decimal columns.
- Never return an exact coordinate from a public endpoint or an unauthenticated query.
- Never compute the approximate point in application code. It is derived in the database.
- Never seed the approximate offset with a random value or a timestamp.
- Do not build seeker-facing map discovery under this ADR.

## Common Mistakes

- Adding decimal coordinate columns because they seem simpler.
- Returning the exact point to the listing owner's own detail endpoint and assuming the
  client will hide it.
- Recomputing the offset per request, producing a drifting approximate location.
- Treating pin capture as optional because the map is not built yet.

## Definition of Done

PostGIS is enabled, listings store an exact geography point captured during creation,
public queries return only the deterministic approximate point, RLS enforces the
distinction, and moderation rejects listings whose pin falls outside the declared area.
