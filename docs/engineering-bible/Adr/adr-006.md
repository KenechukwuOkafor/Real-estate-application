# ADR-006 — Adopt PostgreSQL Full-Text Search Before Introducing Elasticsearch/OpenSearch

## Status

**Accepted**

---

# Context

Search is one of Ruvo's core product capabilities.

Users must be able to quickly discover properties using combinations of:

- Location
- Price
- Property type
- Bedrooms
- Bathrooms
- Amenities
- Verification status
- Availability
- Keywords

As the platform grows, search quality and response time become increasingly important.

Many marketplace platforms adopt dedicated search engines such as:

- Elasticsearch
- OpenSearch
- Algolia
- Meilisearch

However, introducing a distributed search engine significantly increases architectural complexity.

The MVP does not yet have sufficient scale to justify this additional infrastructure.

---

# Decision

Ruvo will use **PostgreSQL Full-Text Search** as the primary search engine during the MVP and early growth stages.

Search functionality will rely on:

- PostgreSQL Full-Text Search
- GIN indexes
- Trigram indexes where appropriate
- Optimized SQL queries
- Pagination
- Ranking
- Filtering

A dedicated search engine will only be introduced after measurable performance limitations have been identified.

---

# Rationale

## 1. Simplicity First

Every new infrastructure component increases:

- Operational cost
- Maintenance effort
- Deployment complexity
- Failure surface

The simplest architecture capable of meeting product requirements should always be preferred.

---

## 2. PostgreSQL Is Already Extremely Capable

PostgreSQL supports:

- Full-text search
- Ranking
- Prefix matching
- Trigram similarity
- Composite indexes
- JSON search
- Geographic extensions

These capabilities are sufficient for Ruvo's expected MVP scale.

---

## 3. Single Source of Truth

Keeping search inside PostgreSQL avoids data duplication.

Without a separate search engine:

- Listings exist once.
- Updates are immediately searchable.
- No synchronization pipeline is required.

This reduces the risk of stale search results.

---

## 4. Lower Operational Complexity

Avoiding Elasticsearch means avoiding:

- Cluster management
- Index synchronization
- Replica configuration
- Version compatibility issues
- Separate monitoring

This allows the engineering team to focus on delivering marketplace features.

---

## 5. Measured Evolution

The architecture should evolve in response to evidence rather than anticipation.

Dedicated search infrastructure should only be adopted when PostgreSQL demonstrably becomes a bottleneck.

---

# Migration Criteria

A dedicated search engine may be introduced when one or more of the following conditions are consistently observed:

- Search latency exceeds agreed service-level objectives.
- Database CPU usage caused by search remains consistently high under production load.
- Search ranking requirements exceed PostgreSQL's capabilities.
- Advanced features such as typo tolerance, synonyms, semantic search, or personalized ranking become product requirements.
- Scaling PostgreSQL further is no longer cost-effective.

These criteria must be supported by production metrics rather than assumptions.

---

# Alternatives Considered

## Elasticsearch

### Pros

- Powerful search capabilities.
- Rich ranking algorithms.
- Horizontal scalability.
- Mature ecosystem.

### Cons

- Separate infrastructure.
- Data synchronization complexity.
- Higher operational overhead.
- Increased deployment complexity.

**Decision:** Deferred.

---

## OpenSearch

### Pros

- Open-source.
- Similar capabilities to Elasticsearch.

### Cons

- Same operational complexity.
- Additional infrastructure burden.

**Decision:** Deferred.

---

## Algolia

### Pros

- Excellent search experience.
- Minimal operational burden.
- Typo tolerance.

### Cons

- Vendor lock-in.
- Additional cost.
- External dependency.
- Separate indexing pipeline.

**Decision:** Deferred.

---

## Meilisearch

### Pros

- Lightweight.
- Easy to operate.
- Good developer experience.

### Cons

- Additional infrastructure.
- Less mature ecosystem.
- Data synchronization still required.

**Decision:** Deferred.

---

# Consequences

## Positive

- Minimal infrastructure.
- Immediate consistency between database and search.
- Lower operational costs.
- Faster MVP delivery.
- Easier debugging.
- Reduced failure modes.

---

## Negative

- Search capabilities are less advanced than dedicated engines.
- Future migration may require indexing infrastructure.
- Complex ranking algorithms may require custom SQL.

---

# Non-Negotiable Constraints

- PostgreSQL is the authoritative search source.
- Search queries must be indexed appropriately.
- Search performance must be monitored.
- Dedicated search engines require a new ADR before adoption.
- Premature optimization is prohibited.

---

# Decision Impact Assessment

## Product Impact

Provides fast and reliable search for the MVP while avoiding unnecessary complexity that could slow feature delivery.

---

## Engineering Impact

Simplifies implementation by keeping search within the existing database architecture and eliminating synchronization concerns.

---

## Operational Impact

Reduces infrastructure, monitoring, and deployment overhead during the early stages of the platform.

---

## Risk Assessment

### Risks

- Search performance may degrade as data volume grows.
- Product requirements may outgrow PostgreSQL's search capabilities.

### Mitigations

- Continuous performance monitoring.
- Query optimization.
- Appropriate indexing.
- Clearly defined migration criteria.

---

# Future Considerations

Potential future enhancements include:

- OpenSearch or Elasticsearch.
- Semantic vector search.
- AI-assisted natural language search.
- Personalized ranking.
- Geospatial proximity ranking.
- Search analytics.

Future adoption must be justified through production metrics and documented in a superseding ADR.

# AI Implementation Guidance

## Context

PostgreSQL Full-Text Search is the approved search implementation for Ruvo.

AI coding agents must assume that all search functionality is implemented using PostgreSQL unless a future ADR supersedes this decision.

## Non-Negotiable Rules

- Prefer SQL-based search.
- Create appropriate indexes.
- Optimize queries before proposing new infrastructure.
- Avoid introducing external search engines without architectural approval.
- Measure performance before optimizing.

## Common Mistakes

- Recommending Elasticsearch without evidence.
- Ignoring PostgreSQL indexing capabilities.
- Building duplicate search indexes unnecessarily.
- Synchronizing data into a separate engine prematurely.

## Definition of Done

Search features achieve the required performance using PostgreSQL, are fully indexed, and remain consistent with the canonical database without requiring external synchronization.
