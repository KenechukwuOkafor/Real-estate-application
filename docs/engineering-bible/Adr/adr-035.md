# ADR-035 — Separate Turnover From Removal With A Rented Listing Status

## Status

Accepted

---

# Context

The Listings Domain describes the end of a listing's life as a single state,
written as **"Unavailable / Archived"**. The schema implemented the second half
of that phrase and not the first: `listing_status` had `archived`, and
`archived` is terminal — migration 0022 added a trigger enforcing terminality
for every caller including `service_role`, on the reasoning that relisting means
creating a new listing, which is also what makes ADR-034's "no quota refund"
position coherent.

Nothing implemented "unavailable". The agent portal shipped a button labelled
**"Mark as rented"** which POSTed to `/archive`. An agent whose property had
simply been let therefore destroyed the listing, and spent another submission
slot to put the same property back up.

The two events in that phrase are not one event:

- **Removal** is *this listing was wrong, or I am done with it.* It is
  permanent, and charging a slot to list the property again is correct, because
  that is new inventory entering the moderation queue.
- **Turnover** is *this property is let for now.* Student housing in Nsukka
  turns over annually. Charging a slot every year for a property that keeps
  coming back charges most exactly the agents with the steadiest inventory —
  the ones the marketplace most wants to keep.

---

# Decision

`listing_status` gains **`rented`**, with two transitions available to the
owning agent and both free:

```
approved  ──────►  rented        mark_own_listing_rented
approved  ◄──────  rented        mark_own_listing_available

approved  ──────►  archived      archive_own_listing   (terminal, unchanged)
```

Both new transitions are `SECURITY DEFINER` functions in the shape
`archive_own_listing` established, because `listings.status` is deliberately not
granted to agents: the privilege that writes `rented` is the privilege that
writes `approved`. Status is governance; no policy is widened to accommodate it.

`rented → archived` is deliberately **not** offered. Widening the one
irreversible transition for a case nobody has reported is not worth it, and the
path already exists at the cost of one extra click: mark available, then remove.

The interface says **"Mark as taken"** rather than "Mark as rented". `shop` is a
property type, so not everything on Ruvo is let to a tenant, and "taken" is what
a student actually says about a room that has gone. `archived` is correspondingly
relabelled from "Taken down" to **"Removed"**, because "taken down" and "taken"
would be one word apart while being opposite in consequence.

---

# The Invariant This Rests On

Marking a listing available returns it to `approved` **with no moderation**.

That is only legitimate because nothing can have changed while it was off the
market, and this ADR exists partly to record how that is enforced — because the
mechanism is an **absence**, and an absence is invisible in review.

`rented` is not in:

1. the `agents_update_own_listings` RLS policy, which admits UPDATE on
   `listings` only where `status in ('draft','rejected')` (ADR/migration 0021); and
2. `EDITABLE_LISTING_STATUSES` in `src/features/listings/editability.ts`, which
   the edit page, the listings page and the write guard all import.

Nothing anywhere names `rented` to make it uneditable. It is uneditable because
two lists do not mention it, by exactly the mechanism that makes `approved`
uneditable.

**The change that breaks this is not subtle and not malicious.** It is somebody
adding `"rented"` to `EDITABLE_LISTING_STATUSES` because agents keep asking to
fix a typo while a place is let. That is a one-word diff, it reads as a kindness,
and it silently converts "mark available" into a publication of unreviewed
content — breaking the guarantee the product sells.

Therefore it is tested by attempt rather than by reading. The probe in
`src/server/repositories/listing-rented-integration.test.ts` PATCHes every column
`authenticated` holds UPDATE on, through PostgREST, as the owning agent, against
a rented listing, and requires all of them to be refused.

The correct editing path stays open: `submit_listing_revision` accepts `rented`,
so a rented listing is corrected the same way an approved one is — proposed,
reviewed, applied. It is the only path, and that is the point.

---

# Rationale

## Turnover is the normal case, so it must be the cheap one

The academic year sets the rhythm. A listing that comes back every August is the
signal of a healthy agent, and the previous design taxed exactly that pattern
while leaving a one-off wrong listing untaxed.

## Slots gate new inventory, not existence

ADR-034's principle is that entitlement gates the moderation queue against
unbounded **new** inventory. A property returning to the market is not new
inventory; it is the same listing, already reviewed and already paid for. This
is the same reading that let ADR/migration 0023 decide a re-review consumes no
slot.

## approved_at is not restamped

`mark_own_listing_available` leaves `approved_at` alone. It records when a
moderator approved this content, and no moderator did anything. Restamping it
would also reorder the dashboard activity feed, which reads that column, and
announce an approval that did not happen — every letting season.

## A rented listing keeps its property's duplicate fingerprint

`listings_duplicate_fingerprint_active_idx` names the statuses in which a listing
holds its property's identity. `rented` is included and `archived` is not,
because they differ in exactly the respect the index cares about: an archived
listing is never coming back, so its property is free to be listed afresh, while
a rented listing **is** coming back and its property is not free.

Excluding it would move the refusal to the wrong day. An agent could submit a
duplicate on Tuesday, and the constraint violation would surface weeks later
when they marked the original available — on the agent who did nothing wrong that
day, for a reason produced by a submission they have forgotten.

# What Does Not Change

Verified before this was written rather than assumed.

**Slots.** `free_listing_quota` is decremented at submission and nothing reads
`listings.status` to decide entitlement. No movement in either direction.

**New inspection requests are blocked.** `create_inspection_request_atomic`
selects the listing `and l.status = 'approved'`, so a rented listing raises
`LISTING_NOT_FOUND`. Correct: it is not in the feed, so nobody should be
arranging to see it.

**Existing inspections survive.** Every site gating on `listings.status` was
enumerated, and the inspection lifecycle appears in none of them: the RLS
policies on `inspection_requests`, `chats` and `messages`, the read-time lapse
evaluation and the completion path all key on the request and its participants.
The seeker with an accepted inspection may well be the person who rented it;
they keep their chat.

**BR-MEDIA-006 now covers rented.** Both cover-image triggers were widened from
`status = 'approved'` to include `rented`. No current write path can strip a
rented listing's cover, but those triggers exist precisely as the backstop that
does not depend on that remaining true — and a rented listing returns to the
market with one call and no review, so it must not be able to arrive there
without a cover.

# Honest Absence For Seekers

A seeker who saved a listing, or was sent the link, previously received
`notFound()` once it left the market — indistinguishable from a mistyped URL.

`listing_absence_notice` returns the reason and three identifying columns
(title, area, city) for a listing that is `rented` **or** `archived`, and nothing
at all for any other status. The two are kept apart because they are different
news: a let property may free up and is worth asking about, a removed one is not.

**A function, not a wider policy.** The obvious alternative is widening
`public_can_read_approved_listings` and relying on the application's own
`.eq("status","approved")` filters to keep the feed clean. Rejected on 0021's
reasoning: the predicate belongs on the policy, not on the three query sites that
happen to filter today and the fourth written next year that forgets.

**Four columns, deliberately.** No price, no description, no photographs. The
storage policy still grants image reads on approved listings only, and an
archived listing may have been removed *because* its price or its photographs
were wrong. A tombstone is the last place to keep serving them.

# Alternatives Considered

## Reuse `archived` and make it reversible

### Pros

- No new enum value, no new functions, no migration split.

### Cons

- Destroys the terminality guarantee 0022 established, which is what makes
  ADR-034's no-refund position coherent.
- Removes the honest permanent option entirely. "I listed the wrong property"
  and "this is let until next August" would again be one button.

## An `is_available` boolean beside `status`

### Pros

- Avoids touching the enum, so no migration split.

### Cons

- Two sources of truth for one question. Every policy, every query and every
  index that reads `status` would need to learn about a second column, and the
  ones that forgot would silently show let properties in search.
- The state machine stops being expressible as a state machine.

## Widen the public SELECT policy for the absence page

Covered above under Honest Absence. Rejected on ADR/migration 0021's reasoning.

# Consequences

## Positive

- An agent with recurring inventory is no longer taxed for turnover.
- The most expensive lie in the portal — a button that said "rented" and meant
  "destroy" — is gone.
- A saved link degrades to an answer instead of a blank 404.
- `archived` keeps its terminality, and its meaning is now unambiguous.

## Negative

- One more status in a lifecycle that already has seven, and every surface
  enumerating status must place it. Mitigated by the `Record<ListingStatus,
  true>` guard in `listing-groups.test.ts`, which fails the build until a new
  status is grouped.
- The safety of the flip back to `approved` rests on an absence from two lists.
  This is the sharpest edge in the design and is stated as such here, in the
  migration, in `editability.ts`, and in the probe that enforces it.
- The enum value must be added in its own migration, because Postgres refuses to
  evaluate a new enum value in the transaction that added it (SQLSTATE 55P04)
  and the fingerprint index evaluates it directly.

---

# Non-Negotiable Constraints

1. `rented` MUST NOT be added to `EDITABLE_LISTING_STATUSES` or to the
   `agents_update_own_listings` policy. Editing a rented listing goes through
   `submit_listing_revision` and nowhere else.
2. `archived` remains terminal for every caller, `service_role` included.
3. Neither transition may touch `free_listing_quota`.
4. `mark_own_listing_available` MUST NOT restamp `approved_at`.
5. Status transitions stay in `SECURITY DEFINER` functions. `listings.status` is
   not granted to `authenticated` and must not become granted.

# AI Implementation Guidance

## Context

`rented` is turnover and `archived` is removal. They are not two names for the
same end state, and the codebase spent one release treating them as one.

## Non-Negotiable Rules

- Never add `rented` to a list of directly-editable statuses. Read the probe in
  `listing-rented-integration.test.ts` before touching either list.
- Never widen `public_can_read_approved_listings` to make a page easier to
  write. Add a `SECURITY DEFINER` function returning the minimum instead.
- Never add an enum value and use it in an index or a policy in the same
  migration file.

## Common Mistakes

- Assuming a rented listing needs re-review to come back. It does not, and the
  reason is that its content cannot have moved.
- Assuming a status conditional that "obviously" renders will render. A branch
  nobody takes shows nothing and reports nothing — seed the status.
- Treating an RLS-refused UPDATE as an error. It is HTTP 200 with zero rows.

## Definition of Done

- The status is placed in every surface that enumerates listing statuses.
- Both transitions are exercised against a real database as the owning agent.
- A rented listing exists in `supabase/seed.sql`.
