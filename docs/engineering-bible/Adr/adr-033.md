# ADR-033 — Store All Listing Media Privately and Serve It Through Signed URLs

## Status

Accepted

---

# Context

The architecture documents state two positions that cannot both survive contact with the
moderation model:

- Security Architecture: public listing images are stored in controlled public buckets.
- Media Architecture: media is served through CDN-backed public URLs, with signed URLs
  reserved for private assets.

Both assume that "listing image" and "public image" are the same thing. They are not.

A listing image exists from the moment an agent uploads it, which is before submission,
before review, and before any approval decision. Under a public bucket, that image is
world-readable by URL from upload onward. This means:

- Images on drafts that were never submitted are public.
- Images on listings a moderator explicitly rejected are public.
- Images on archived listings remain public indefinitely.
- Withdrawing a listing from public view does not withdraw its images.

The moderation decision therefore governs the listing record while having no effect on the
media attached to it. A rejected listing is a listing whose photographs are still served.

The same objects also carried original filenames in their storage paths, and the bucket
performed no size or MIME validation.

---

# Decision

All listing media is stored in private buckets and served through short-lived signed URLs
generated at render time.

1. **Buckets are private.** No listing media has a public URL.
2. **Reads are signed server-side.** Signed URLs are generated during render, for the
   specific viewer and the specific listing state.
3. **Signing is conditional on listing state.** A signed URL is issued for an approved
   listing to any viewer. For any other state it is issued only to the owning agent or an
   administrator.
4. **No public URL is stored.** A column holding a permanently valid URL is a public bucket
   by another name.
5. **Storage paths are opaque.** Generated identifiers plus extension. Original filenames
   may be retained as database metadata and never appear in a path or URL.
6. **Validation is enforced at the bucket.** Size limits and accepted MIME types are bucket
   configuration, not only application checks.
7. **Verification documents are separately private** with a shorter lifetime, readable only
   by the owning agent and administrators.

Media visibility semantics are unchanged: images become viewable by the public when the
listing is approved. What changes is that the platform enforces it rather than assuming it.

---

# Signed URL Lifetimes

Lifetime is a trade between cache effectiveness and the durability of a leaked link.

| Asset | Lifetime | Reasoning |
|---|---|---|
| Listing images | 1 hour | Long enough that a page view and its repeat visits reuse one URL. Short enough that a link pasted elsewhere is dead before it is opened, and shorter than any plausible moderation turnaround. |
| Verification documents | 60 seconds | Consumed once, immediately, by an administrator during review. There is no caching benefit to trade away. |

These are configuration values, not constants embedded in query code.

---

# Rationale

## Moderation must govern what is served, not only what is listed

The purpose of review is to decide what the public sees. A model in which rejection leaves
the photographs publicly retrievable does not implement that decision. This is the
argument that overrides the documented position.

## A permanently valid URL is a public bucket

Storing a non-expiring URL alongside a private object reproduces the exposure while
appearing to have closed it. The column is removed rather than repurposed.

## Enforcement belongs at the bucket

Application-level size and type checks are bypassed by any path that does not call them.
Bucket configuration is not.

---

# Alternatives Considered

## Keep the bucket public, move objects on approval

### Pros

- Retains CDN caching for approved listings.
- Approved images cost nothing to serve.

### Cons

- Every state transition becomes a file operation that can partially fail.
- A moderator's decision depends on a copy succeeding.
- Images are still public between upload and rejection.

Decision: Rejected. Correctness of the moderation boundary should not depend on file moves.

---

## Two buckets, public for approved and private for everything else

### Pros

- Approved media keeps public caching.
- The boundary is explicit in storage layout.

### Cons

- Same file-movement fragility as above.
- Rejection after approval requires removing an object that may be cached downstream.

Decision: Rejected for the same reason. Reconsider only if delivery cost forces it.

---

## Accept the documented position

### Pros

- Matches existing documents. No amendment needed.
- Best possible delivery performance.

### Cons

- Draft and rejected listing images remain world-readable.
- The moderation decision has no effect on media.

Decision: Rejected.

---

# Consequences

## Positive

- Media visibility now follows the listing lifecycle.
- Rejected and draft images are not retrievable by the public.
- A leaked URL expires.
- Storage paths reveal nothing about the uploader or the original file.
- Size and type limits are enforced where they cannot be bypassed.

## Negative

- **CDN caching is lost.** Every image byte is served from origin. Bandwidth cost rises,
  and bandwidth is already the platform's largest variable cost.
- Rendering a listing requires signing work per image.
- Signed URLs cannot be embedded in cacheable static output.
- Seed data must include real stored objects, because a path with no object behind it now
  produces a URL that fails.

---

# Interaction With Image Processing

This decision increases the cost of serving unoptimized images, because the caching that
previously absorbed some of that cost is gone.

ADR-015's processing pipeline was already justified on cost and performance grounds. This
decision strengthens that justification and raises its priority: optimized derivatives are
now partly compensating for a regression introduced here, not only an improvement.

Whether a delivery-time transformation service can operate on signed URLs is an open
question that materially affects how the pipeline is built.

---

# Non-Negotiable Constraints

- No listing media bucket is public.
- No permanently valid media URL is stored in the database.
- Signed URLs for non-approved listings are issued only to the owning agent or an administrator.
- Storage paths never contain original filenames.
- Size and MIME restrictions exist at the bucket, not only in application code.
- Verification documents are never readable by any party other than the owning agent and administrators.
- Signed URL lifetimes are configuration.

---

# Decision Impact Assessment

## Product Impact

Moderation decisions now have force over media. A rejected listing's photographs stop being
retrievable.

## Engineering Impact

Render paths must sign. Seeds must contain real objects. Any future public-URL assumption is
a regression.

## Operational Impact

Origin bandwidth increases. Image optimization becomes more urgent.

## Risk Assessment

### Risks

- Bandwidth cost rises before optimization lands.
- A future contributor reintroduces a stored public URL for convenience.
- Signing latency becomes noticeable on listing pages with many images.

### Mitigations

- Prioritize the processing pipeline accordingly.
- The absence of a public URL column is itself the guard; reintroducing one requires a migration.
- Signing is batched per render.

---

# Open Questions

- Can a delivery-time image transformation service operate on privately stored objects? The
  answer determines whether optimized delivery needs a processing pipeline or only a
  transformation layer.
- Is 1 hour the right image lifetime once real traffic exists?
- Does any future public-facing asset class justify a genuinely public bucket?

# AI Implementation Guidance

## Context

Listing media is private. Access is granted per render through short-lived signed URLs,
conditional on listing state and viewer.

## Non-Negotiable Rules

- Never create a public media bucket.
- Never store a media URL in the database. Store the path; sign at render.
- Never issue a signed URL for a non-approved listing to anyone but the owner or an administrator.
- Never place an original filename in a storage path.
- Never rely solely on application code for size or MIME limits.

## Common Mistakes

- Adding a `public_url` column back because signing per render seems wasteful.
- Signing once and caching the URL beyond its lifetime.
- Signing before checking listing state, so the check becomes advisory.
- Seeding storage paths with no objects behind them, which works until reads are signed.

## Definition of Done

All listing media buckets are private, reads are signed per render and gated on listing
state, no stored URL exists, paths are opaque, and bucket configuration enforces size and
type.
