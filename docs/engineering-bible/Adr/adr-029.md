# ADR-029 — Treat Documentation as Code

## Status

Accepted

---

# Context

Software architecture inevitably evolves.

When documentation exists separately from implementation, it quickly becomes outdated.

Outdated documentation is often more harmful than having no documentation because it creates false confidence and poor engineering decisions.

As Ruvo grows, documentation must evolve alongside the codebase rather than becoming an afterthought.

---

# Decision

Ruvo adopts **Documentation as Code**.

Architecture documentation, engineering standards, operational procedures, and decision records are maintained within the same version-controlled repository as the source code.

Documentation changes follow the same engineering workflow as application code.

---

# Documentation Principles

Documentation must be:

- Version controlled
- Peer reviewed
- Discoverable
- Searchable
- AI-readable
- Continuously maintained

Documentation is considered a production asset.

---

# Scope

Documentation includes:

- Product documentation
- Domain models
- Architecture
- ADRs
- Engineering standards
- Operations playbooks
- Runbooks
- API references
- Diagrams
- Development workflows

---

# Documentation Workflow

```
Architecture Change

↓

Documentation Updated

↓

Peer Review

↓

Merged

↓

Published
```

Documentation updates are expected as part of feature delivery.

---

# Rationale

## Knowledge Preservation

Architectural knowledge remains available long after implementation.

---

## Team Alignment

Documentation provides a shared understanding across engineering, product, and operations.

---

## AI Readability

Structured documentation enables AI coding agents to reason about the system accurately.

---

## Maintainability

Documentation evolves alongside implementation rather than lagging behind.

---

# Alternatives Considered

## Wiki-Based Documentation

### Pros

- Easy editing.

### Cons

- Version drift.
- Weak review process.
- Poor traceability.

Decision:

Rejected.

---

## Documentation After Development

### Pros

- Faster initial implementation.

### Cons

- Frequently forgotten.
- Rapidly outdated.

Decision:

Rejected.

---

# Consequences

## Positive

- Better onboarding.
- Reduced knowledge loss.
- Higher architectural consistency.
- Improved AI effectiveness.

## Negative

- Additional effort during development.
- Documentation review becomes part of engineering work.

---

# Non-Negotiable Constraints

- Significant architectural changes require documentation updates.
- ADRs accompany major architectural decisions.
- Documentation resides in version control.
- Documentation quality is part of Definition of Done.

---

# Decision Impact Assessment

## Product Impact

Improves long-term product consistency.

## Engineering Impact

Establishes documentation as a first-class engineering artifact.

## Operational Impact

Provides reliable reference material for maintenance and incident response.

# AI Implementation Guidance

Always consult documentation before implementing architectural changes.

Update documentation whenever architectural intent changes.

Treat stale documentation as a defect.

## Definition of Done

Architecture and engineering documentation remain synchronized with the implemented system through version-controlled workflows.
