# ADR-009 — Adopt UUIDs as the Primary Identifier Strategy

## Status

Accepted

---

# Context

Every entity within Ruvo requires a globally unique identifier.

Examples include:

- Users
- Agents
- Listings
- Images
- Videos
- Messages
- Reports
- Payments
- Inspections

Choosing an identifier strategy affects security, scalability, interoperability, and future architectural evolution.

Traditional auto-incrementing integers expose internal record counts and enable resource enumeration.

The platform requires identifiers that remain unique across distributed systems without leaking implementation details.

---

# Decision

Ruvo will use **UUID Version 4** as the primary identifier for all externally accessible entities.

Integer-based primary keys will not be used.

UUIDs become the canonical identifier across:

- Database
- APIs
- URLs
- Events
- Logs
- Audit records

---

# Rationale

## Security

Sequential IDs allow attackers to guess resource identifiers.

Example:

```
/listing/1001
/listing/1002
/listing/1003
```

UUIDs make enumeration impractical.

---

## Distributed Generation

UUIDs can be generated independently.

No central sequence generator is required.

This simplifies future distributed services.

---

## Data Migrations

UUIDs greatly simplify:

- imports
- exports
- backups
- synchronization

without identifier collisions.

---

## Event Architecture

Events reference globally unique identifiers.

Example:

```
ListingApproved

listingId

agentId
```

These identifiers remain globally unique.

---

## API Stability

Public APIs should never expose implementation details.

UUIDs provide stable public identifiers regardless of database implementation.

---

# Alternatives Considered

## Auto Increment Integers

### Pros

- Simple
- Small indexes
- Familiar

### Cons

- Enumeration attacks
- Difficult merges
- Distributed limitations

Decision:

Rejected.

---

## ULIDs

### Pros

- Sortable
- Human-friendly

### Cons

- Additional implementation complexity.
- Limited practical benefit for current requirements.

Decision:

Deferred.

---

# Consequences

## Positive

- Better security
- Better scalability
- Cleaner APIs
- Easier synchronization

## Negative

- Larger indexes
- Less readable manually

---

# Non-Negotiable Constraints

- Public entities use UUIDs.
- IDs are immutable.
- UUIDs are never recycled.
- URLs expose UUIDs only.

---

# Decision Impact Assessment

## Product Impact

Users interact with opaque identifiers that do not reveal business information.

## Engineering Impact

Simplifies distributed architecture and future integrations.

## Operational Impact

Reduces identifier conflicts during migrations and restores.

## Risk Assessment

Risks:

- Larger indexes.

Mitigation:

Proper PostgreSQL indexing.

Always generate UUID primary keys for new entities.

Never expose sequential internal identifiers.

Never build APIs around integer IDs.

Every externally accessible entity is identified using UUIDs.
