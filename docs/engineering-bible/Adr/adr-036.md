# ADR-036 — Identify A Public Agent Profile By A Handle Derived Once

## Status

Accepted

---

# Context

The public agent profile at `/a/<handle>` is not a navigation surface. It is a
link an agent pastes into a WhatsApp bio, a status, or a flyer: one URL, always
current, carrying a verified mark that a Facebook housing group cannot issue.
Every decision below follows from that and from nothing else.

Listings already solved shareable identity, in `parseListingIdentifier`:

```
/listings/modern-flat--0198c1f2-3a4b-7c8d-9e0f-1a2b3c4d5e6f
```

A slug for humans, a `public_uuid` for resolution, split on the final double
dash. The slug may drift freely because the uuid is what resolves, so a
retitled listing keeps working and every previously shared link still lands.

The obvious move was to reuse it.

---

# Decision

**Do not reuse `slug--public_uuid`. Identify an agent profile by a `handle`:
unique across all agents, derived from the display name ONCE at profile
creation, and never re-derived.**

## Why the listing scheme does not transfer

A listing link is **clicked**. It arrives in a feed or a message, nobody reads
it, and the uuid tail costs nothing.

An agent profile link is **typed, forwarded, and read** — by a stranger
deciding whether this person is real.

```
/listings/modern-flat--0198c1f2-3a4b-7c8d-9e0f-1a2b3c4d5e6f   fine
/a/prime-homes-nsukka--0198c1f2-3a4b-7c8d-9e0f-1a2b3c4d5e6f   not fine
```

Fifty-seven characters, impossible to repeat aloud, and it looks
machine-generated — on the one page whose entire job is looking legitimate.
The identifier stops being plumbing here and becomes part of the pitch. That is
the whole of the difference, and it is why a pattern that is correct elsewhere
in this codebase is the wrong pattern for this surface.

## Derive-once is the load-bearing half

The requirement the uuid was serving is stability under rename. Deriving once
and never re-deriving serves it **more completely**, not less:

| | listing `slug--public_uuid` | agent `handle` |
|---|---|---|
| after a rename | the slug drifts; the uuid still resolves | nothing moves |
| an old shared link | resolves, then canonical-redirects | is still the current link |
| what the recipient sees | a URL that no longer matches the title | the URL the agent gave them |

The asymmetry is the point. **A renamed agent keeping their working link
matters more than a reference that merely survives renaming**, because the link
is already sitting in somebody's WhatsApp bio and on somebody's flyer. A
redirect is a good answer for a link someone clicks today; it is a weak answer
for a link that was copied into a bio six months ago and is now the only
address anyone has for that business.

Renaming "Prime Homes Nsukka" to "Prime Property Group" therefore leaves
`/a/prime-homes-nsukka` correct, not merely functional.

The corollary is that a handle is **not user-editable**. A handle that can
change is a link that can break, and every previously pasted URL is somebody
else's message history. Reassignment is an admin action when it becomes one,
the same shape as clearing an avatar.

## The database assigns it, and no role may write it

`authenticated` holds `insert (bio, display_name, user_id)` on
`agent_profiles`. Adding `handle` to that grant would make the namespace
claimable by anyone with a session token and curl: register `ruvo`, or a
competitor's business name before they sign up.

The application choosing a candidate politely does not matter. ADR-010
Amendment 1 records a self-verification hole whose entire shape was *"the
application never does this; PostgREST is exposed"*.

So `handle` is granted for neither `INSERT` nor `UPDATE`, and a `BEFORE INSERT`
trigger assigns it. The caller cannot choose, cannot squat, and cannot rename.
A `CHECK` constraint enforces the shape independently, so a `service_role`
write or a later migration cannot introduce a handle the router will not match.

## Collisions take a counter

`prime-homes-2`, not `prime-homes-x7f`. The counter tells the agent something
true — somebody got there first — while a random suffix tells them nothing and
reads as an error on a page that is asking to be trusted. Assignment loops on
the unique index rather than reading first, because a check-then-insert races
two agents registering the same business name in the same second.

## The cost, accepted

A global namespace. Two agents cannot both be `prime-homes`, and a handle is an
impersonation surface in a way an opaque id is not. Bounded by three things:
verification already gates public visibility and requires documents, a reserved
list refuses the words that would read as Ruvo speaking (`support`, `official`,
`verified`, `admin`, `ruvo`), and admins can reassign.

---

# Consequences

- The derivation exists in SQL (assignment, which must be privileged) and in
  TypeScript (shape validation, which the route needs before it queries). Two
  implementations of one rule, pinned by a differential test driving both from
  the same inputs — the mitigation ADR-010 Amendment 1 requires for exactly
  this shape.
- `handle` joins the `anon` column grant. It is the only column the route
  filters on, and the page cannot resolve without it.
- An unverified agent has a handle and a page. Neither is publicly visible,
  which falls out of `public_can_read_verified_agent_profiles` rather than
  being separately enforced.
