# ADR-034 — Grant Listing Entitlement Through Quota Before Subscriptions Exist

## Status

Accepted

---

# Context

The Subscriptions domain states in BR-SUB-001 that an active subscription is required to
publish new listings.

The database contains a `free_listing_quota` column on agent profiles and a
`founding_agent` flag. Neither appears in the Subscriptions domain specification, ADR-020,
or any other document. They are schema without a decision behind them.

The consequence was a platform on which no agent could publish anything. The quota column
defaulted to zero and no code raised it. The only other route to entitlement was a
subscription row, and no code path could create one because no payment integration exists.
The entitlement check therefore refused every agent on their first action. This was
discovered by scan, not by testing, because seed data set the quota to a non-zero value and
concealed the condition.

Ruvo will onboard its first agents in Nsukka by direct recruitment, before payment is
built. Those agents must be able to list. Requiring a subscription that cannot be purchased
is not a policy; it is a deadlock.

---

# Decision

Listing entitlement is satisfied by **either** an active subscription **or** remaining free
listing quota.

1. **Quota is granted on verification approval.** When an administrator approves an agent's
   verification, the agent receives a fixed allowance of listing slots if they currently
   have none. An existing non-zero allowance is never overwritten.
2. **Drafts are not entitlement-gated.** An agent may create and edit drafts freely,
   regardless of verification status or quota. Entitlement is checked when a listing is
   submitted for review.
3. **Submission consumes a slot.** The allowance is a counter, decremented on successful
   submission.
4. **Verification remains a separate gate.** An unverified agent cannot submit regardless of
   quota. Quota answers "how many"; verification answers "at all".
5. **Quota cannot be self-granted.** The column is not writable by the agent. Only
   administrative approval grants it.
6. **The allowance is configuration**, not a constant embedded in business logic.

BR-SUB-001 is amended to read: publishing a new listing requires an active subscription or
remaining free listing quota.


---

# The Underlying Principle

**Entitlement gates the moderation queue, never the workspace.**

Every subscription rule should be readable against that sentence.

Drafting, editing and preparing a listing are workspace activities. They
produce no marketplace inventory and consume no reviewer time, so no
entitlement applies to them at any point. Submission is where work enters a
queue a human must process, and that is the only place entitlement is checked.

This is what settles wording like "expired agents cannot create new listings",
which is ambiguous between drafting and publishing and was read both ways.
Under this principle it means publishing. BR-SUB-003, BR-SUB-004 and BR-SUB-005
were reworded accordingly.

The practical consequence is that an agent whose entitlement lapses keeps a
working workspace. They can continue preparing listings; they simply cannot put
them in front of a reviewer until entitlement is restored. Nothing already
approved is withdrawn.

---

# Why Verification Approval Is the Grant Point

Three candidate moments were available: signup, verification approval, and manual
administrative action.

Verification approval is chosen because it is already the gate on submission. Attaching the
allowance to the same event means one decision governs both questions, rather than two
gates that can disagree.

It also protects the moderation queue. An unverified account cannot place anything in front
of a human reviewer. When agent signup opens beyond direct recruitment, that protection is
already in place rather than needing to be added.

Granting at signup was rejected for the opposite reason: it would allow anyone creating an
account to submit listings for review, making the moderation queue the first line of defence
against spam rather than the last.

Manual administrative grant was rejected as an unnecessary step on every onboarding, and one
more screen to build.

---

# Relationship to Subscriptions

Quota is not a subscription tier and must not become one.

It is a finite allowance granted once, on verification, to make the platform usable before
payment exists. When subscriptions arrive:

- An agent with remaining quota continues to use it.
- Quota is not replenished by subscribing, and subscribing does not consume it.
- The two are checked independently. Either satisfies entitlement.
- No subscription plan is defined in terms of quota.

The carve-out is expected to persist for founding agents rather than being removed. Agents
recruited before payment existed should not lose access when it arrives.

---

# Rationale

## The rule as written was unimplementable

A requirement that can only be satisfied by a mechanism that does not exist is not a
constraint on behaviour. Amending the document is more honest than leaving code and
specification in silent disagreement, which is how this was found in the first place.

## Undocumented schema becomes undocumented behaviour

`free_listing_quota` and `founding_agent` existed as columns with no decision behind them.
That is how a deadlock reached the database unnoticed. Recording the decision is the point
of this ADR as much as the policy itself.

## Separating drafts from entitlement matches how agents work

An agent should be able to prepare a listing while their verification is pending. Gating
draft creation on entitlement meant the first action a new agent attempted was the one that
failed.

---

# Alternatives Considered

## Enforce BR-SUB-001 as written and build payments first

### Pros

- No divergence between document and code.
- One entitlement mechanism.

### Cons

- Blocks all agent onboarding behind a payment integration.
- Requires the first recruited agents to pay before the platform has proven anything.

Decision: Rejected.

---

## Grant quota at signup

### Pros

- Simplest. One line at profile creation.
- Agents can trial the full flow immediately.

### Cons

- Any account can place listings in the moderation queue.
- Moderation becomes the anti-spam mechanism rather than a quality mechanism.

Decision: Rejected.

---

## Unlimited listings until subscriptions ship

### Pros

- No counter, no grant logic.

### Cons

- No natural transition when payment arrives.
- Nothing bounds a misbehaving account.

Decision: Rejected.

---

# Consequences

## Positive

- Agents can be onboarded before payment exists.
- The moderation queue is protected from unverified accounts.
- Drafting is unblocked while verification is pending.
- A previously undocumented mechanism is now recorded.

## Negative

- Two entitlement mechanisms must coexist indefinitely.
- Founding agents hold an allowance that later agents do not, which is a fairness question
  when pricing is communicated.
- The allowance size is a judgement with no evidence behind it yet.

---

# Non-Negotiable Constraints

- Entitlement is satisfied by an active subscription **or** remaining quota. Never only one.
- Quota is granted solely by administrative verification approval.
- An existing non-zero quota is never overwritten by a grant.
- The quota column is never writable by the agent.
- Draft creation is never entitlement-gated.
- Verification remains an independent gate on submission.
- The allowance value is configuration.
- Every grant and consumption is audited.

---

# Decision Impact Assessment

## Product Impact

Makes agent onboarding possible before payment. Establishes that founding agents retain
their allowance when subscriptions arrive.

## Engineering Impact

Entitlement has two sources permanently. Any future check must consider both.

## Operational Impact

Administrators grant listing capacity implicitly when approving verification. That
consequence should be visible in the review interface.

## Risk Assessment

### Risks

- The allowance proves too small or too generous with no data to judge by.
- Agents perceive unfairness when later agents must pay for what founders received.
- A future contributor treats quota as a subscription tier.

### Mitigations

- The value is configuration and can change without a migration.
- Founding status is recorded, so the distinction can be communicated deliberately.
- This ADR states explicitly that quota is not a tier.

---

# Open Questions

- What allowance size is right, once there is evidence?
- Does quota ever replenish, or is it strictly once?
- When subscriptions ship, do founding agents keep the allowance permanently or for a period?
- Should `founding_agent` drive any behaviour, or remain descriptive?

# AI Implementation Guidance

## Context

An agent may submit a listing for review if they hold an active subscription or have
remaining free listing quota, and are verified.

## Non-Negotiable Rules

- Never gate draft creation on entitlement.
- Never treat a subscription as the only path to entitlement.
- Never allow an agent to write their own quota column.
- Never overwrite an existing non-zero quota when granting.
- Never bypass verification because quota is present, or vice versa.

## Common Mistakes

- Implementing BR-SUB-001 literally and deadlocking new agents.
- Reporting an action as available when the entitlement check will refuse it.
- Granting quota at signup rather than at verification approval.
- Embedding the allowance as a literal in service code.

## Definition of Done

Entitlement accepts either source, quota is granted only on verification approval and never
overwritten, drafts are ungated, and every grant and consumption is audited.
