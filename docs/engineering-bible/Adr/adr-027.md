# ADR-027 — Adopt a Background Jobs Architecture for Asynchronous Processing

## Status

Accepted

---

# Context

Not every operation should execute during an HTTP request.

Many business processes are computationally expensive, slow, or involve external systems.

Examples include:

- Image processing
- Video transcoding
- Email delivery
- Push notifications
- Subscription reminders
- AI-powered analysis
- Search indexing
- Report generation

Executing these tasks synchronously increases response times, reduces reliability, and creates poor user experiences.

---

# Decision

Ruvo adopts a dedicated Background Jobs Architecture for all long-running and asynchronous work.

User-facing requests should complete as quickly as possible.

Non-critical work is delegated to background workers.

---

# Job Lifecycle

```
Job Created

↓

Queued

↓

Reserved

↓

Executing

↓

Completed

OR

Failed

↓

Retry

↓

Dead Letter Queue (if retries exhausted)
```

Every transition is observable and auditable.

---

# Responsibilities

Background workers are responsible for:

- Media processing
- Notification delivery
- Email sending
- AI tasks
- Search indexing
- Scheduled maintenance
- Data cleanup
- Analytics aggregation

Workers never handle user authentication directly.

---

# Design Principles

## Asynchronous by Default

Expensive work should execute outside user requests.

---

## Idempotency

Jobs must be safe to execute multiple times.

---

## Retry Support

Transient failures are retried automatically.

---

## Isolation

Worker failures must not interrupt user-facing APIs.

---

## Observability

Every job emits metrics, logs, and status updates.

---

# Rationale

## Better User Experience

Users receive immediate responses while background work continues independently.

---

## Scalability

Workers can scale independently of web servers.

---

## Reliability

Retries reduce failures caused by temporary outages.

---

## Future Growth

The architecture supports AI workloads, scheduled automation, and large-scale processing without redesign.

---

# Alternatives Considered

## Synchronous Processing

### Pros

- Simple implementation.

### Cons

- Slow requests.
- Poor scalability.
- Timeout risks.

Decision:

Rejected.

---

## Cron Jobs Only

### Pros

- Easy scheduling.

### Cons

- Unsuitable for event-driven workloads.
- Limited retry capabilities.

Decision:

Rejected.

---

# Consequences

## Positive

- Faster APIs.
- Independent scaling.
- Improved reliability.
- Better fault isolation.

## Negative

- Additional infrastructure.
- Queue management complexity.

---

# Non-Negotiable Constraints

- Jobs must be idempotent.
- Retry behaviour must be configurable.
- Failures must be observable.
- Background work must never block user interactions.

---

# Decision Impact Assessment

## Product Impact

Creates a faster and more responsive user experience.

## Engineering Impact

Separates asynchronous work from request handling.

## Operational Impact

Introduces monitoring, queue management, and worker scaling.

# AI Implementation Guidance

Never perform expensive work inside request handlers when asynchronous execution is appropriate.

Design jobs to tolerate retries and partial failures.

Keep workers stateless whenever possible.

## Definition of Done

Long-running tasks execute through managed background workers with retries, observability, and independent scalability.
