# ADR-015 — Adopt an Asynchronous Image Processing Pipeline

## Status

Accepted — **amended by ADR-015-A1**.

> **Amendment 1 (ADR-015-A1) applies to this decision.**
>
> Supabase image transformation works on privately stored objects, through the
> signed-URL path specifically. That was unknown when this ADR was written and
> it removes most of the pipeline below **for images**.
>
> Superseded for images: responsive variant generation, thumbnail generation,
> optimization and format conversion as pipeline stages, storage of
> derivatives, and selection among stored derivatives at delivery. Sizes are
> produced by passing `transform` to `createSignedUrl` instead.
>
> Standing unchanged: MIME validation, virus scanning, EXIF extraction and
> metadata normalization, storage verification — transformation performs none
> of these. The rule that clients never receive original uploads also stands,
> now enforced by a signed URL whose transform options cannot be altered.
>
> **ADR-016 is unaffected.** Video still needs the full pipeline as written,
> and the queue's `media` lane exists for it.
>
> Read ADR-015-A1 alongside this document. Building variant generation from the
> pipeline diagram below does not satisfy ADR-015.

> **Unblocked by ADR-032.**
>
> This decision requires image processing to be asynchronous and forbids doing
> it in the request. That made it unimplementable while no queue, jobs table or
> scheduler existed — processing was deferred slice after slice for want of a
> mechanism, not for want of intent.
>
> ADR-032 supplies that mechanism. This ADR is now implementable and its
> asynchronous requirement is binding rather than aspirational.

---

# Context

Images are one of the most important assets in a real estate marketplace.

A single listing may contain multiple high-resolution photographs captured from different devices.

Raw uploads are unsuitable for direct delivery because they often have:

- Excessive file sizes
- Inconsistent dimensions
- Incorrect orientation
- Embedded metadata
- Slow loading times

Performing image optimization during the upload request would significantly increase response time and degrade the user experience.

---

# Decision

Ruvo will process all uploaded images asynchronously.

Uploading an image and preparing it for public delivery are treated as separate operations.

After upload, images enter a background processing pipeline before becoming publicly available.

---

# Image Processing Pipeline

Every uploaded image follows this lifecycle:

```
Upload

↓

Virus Scan

↓

Metadata Extraction

↓

Orientation Correction

↓

Compression

↓

Responsive Variant Generation

↓

Thumbnail Generation

↓

Optimization

↓

Storage

↓

Published
```

Each stage produces structured events for monitoring and retry handling.

---

# Processing Responsibilities

The pipeline performs:

- MIME validation
- Virus scanning
- EXIF extraction
- Orientation correction
- Metadata normalization
- Compression
- Thumbnail generation
- Responsive image generation
- WebP/AVIF conversion where supported
- Storage verification

---

# Delivery Strategy

Clients never receive original uploads directly.

Instead, optimized derivatives are served according to device requirements.

Examples include:

- Thumbnail
- Small
- Medium
- Large
- Original (restricted)

Selection is automatic based on viewport and network conditions.

---

# Background Processing

Image optimization must never block user interactions.

Processing is delegated to background workers capable of:

- Retry handling
- Failure reporting
- Progress tracking
- Parallel execution

---

# Rationale

## Performance

Optimized images reduce bandwidth and improve page load times.

---

## User Experience

Uploads complete quickly while optimization continues independently.

---

## Scalability

Processing workloads can scale independently of the application servers.

---

## Future Extensibility

The pipeline can later incorporate:

- AI quality scoring
- Automatic tagging
- Duplicate detection
- Watermarking
- Content moderation

without affecting the upload API.

---

# Alternatives Considered

## Synchronous Processing

### Pros

- Simple implementation.

### Cons

- Slow uploads.
- Poor user experience.
- Reduced scalability.

Decision:

Rejected.

---

## No Optimization

### Pros

- Minimal infrastructure.

### Cons

- Large payloads.
- Poor performance.
- Excessive storage costs.

Decision:

Rejected.

---

# Consequences

## Positive

- Faster uploads.
- Better performance.
- Consistent image quality.
- Independent scalability.

## Negative

- Additional infrastructure.
- Background job complexity.

---

# Non-Negotiable Constraints

- Original uploads are preserved.
- Optimized variants are generated automatically.
- Processing is asynchronous.
- Failed jobs are retryable.
- Metadata is retained independently of storage.

---

# Decision Impact Assessment

## Product Impact

Improves browsing speed and listing quality across all supported devices.

## Engineering Impact

Separates upload concerns from media optimization and delivery.

## Operational Impact

Enables independent monitoring and scaling of image workloads.

# AI Implementation Guidance

Never perform expensive image processing during the upload request.

Always use background workers.

Clients should receive optimized images rather than original uploads.

## Definition of Done

Images progress through the full processing pipeline, optimized variants are generated automatically, and delivery is responsive and bandwidth-efficient.
