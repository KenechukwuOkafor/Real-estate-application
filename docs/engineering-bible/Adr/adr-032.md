# ADR-032 — Adopt a Postgres-Backed Job Queue Drained by Scheduled Invocation

## Status

Accepted

---

# Context

Several accepted decisions require work to happen outside the request that triggers it.
None of them can be implemented today, because no mechanism exists to run deferred work.

- ADR-015 requires image processing to be asynchronous and explicitly forbids performing
  it during the upload request.
- ADR-016 requires the same for video.
- The Notifications domain requires delivery across in-app, email, and WhatsApp, each of
  which fails in ways that need retry.
- Media Architecture specifies cleanup of orphaned images, orphaned videos, expired
  uploads, and unused thumbnails.

The application runs as serverless functions on Vercel. A serverless function cannot host
a long-lived worker process. There is no queue, no job table, and no scheduler.

This is currently the blocking dependency for three separate areas of work, and it has
already forced one slice to be split.

A second consideration shapes the choice. The platform recently replaced a three-write
sequence with a single atomic database function, because a partially applied sequence
could strand an inspection request with no conversation attached. The same hazard applies
to enqueuing work: if a job is enqueued outside the transaction that produced the state
change, the two can diverge. A listing can be approved with no notification enqueued, or
a notification can be enqueued for an approval that rolled back.

---

# Decision

Ruvo will implement background work as a job table in the primary PostgreSQL database,
drained by a scheduled invocation of an application route.

Specifically:

1. **Jobs are rows.** A `jobs` table in the primary database holds queued work, with a
   type, a payload, a status, an attempt count, and a scheduled time.
2. **Jobs are enqueued transactionally.** A job is inserted in the same transaction as
   the domain write that causes it. Either both land or neither does.
3. **A scheduled invocation drains the queue.** A protected application route claims a
   batch of due jobs, executes them, and records the outcome.
4. **Claiming is atomic.** Jobs are claimed with `SELECT ... FOR UPDATE SKIP LOCKED` so
   that overlapping invocations cannot process the same job twice.
5. **Failures retry with backoff.** A failed job increments its attempt count and is
   rescheduled. After a defined maximum it moves to a terminal failed state and is
   surfaced for inspection rather than silently discarded.
6. **Handlers are idempotent.** Every job type must tolerate being executed more than
   once, because at-least-once delivery is the guarantee this design provides.

---

# The Outbox Property

The decisive property of this design is that the queue lives in the same database as the
domain data.

```
BEGIN
  UPDATE listings SET status = 'approved' ...
  INSERT INTO jobs (type, payload) VALUES ('notify.listing_approved', ...)
COMMIT
```

There is no window in which one has happened and the other has not. No external system
can be unreachable at the moment of enqueue. No compensating logic is required.

An external queue cannot offer this. Enqueuing to a separate service is a network call
that can fail after the transaction commits, or succeed before it rolls back. Recovering
from that requires either a local outbox table anyway, or acceptance of lost and phantom
jobs.

---

# What This Is Not

This is not a general-purpose distributed task system, and should not grow into one.

It is suitable for work that is:

- Deferrable by seconds to minutes
- Idempotent
- Bounded in duration by the serverless function limit
- Low enough in volume that a periodic batch keeps pace

It is unsuitable for work that is:

- Latency-sensitive in the sub-second range
- Long-running beyond the function timeout
- High-throughput enough that polling becomes the bottleneck

If a future workload violates those bounds, that is the trigger for a superseding
decision, not for stretching this one.

---

# Rationale

## Transactional enqueue eliminates a class of bug the platform has already hit

The inspection creation path was made atomic precisely because partial application
stranded records. Enqueuing outside a transaction reintroduces that hazard at every
future call site. Choosing the design that makes the bug impossible is worth more than
the operational conveniences of a managed queue.

## The execution environment must run Node

Image processing requires native image libraries. Notification delivery requires outbound
HTTP with retry. Neither is available inside a Postgres scheduled function, and native
image libraries are awkward in edge runtimes. Draining through an application route means
handlers run in the same environment as the rest of the codebase, with the same
dependencies, the same error reporting, and the same tests.

## Observability comes free

Jobs are rows in a database that is already inspected daily. Queue depth, failure rates,
and stuck jobs are ordinary queries. No new dashboard, no new vendor console.

## No new vendor at this stage

The platform has no users and no revenue. Adding a queue provider means another account,
another secret, another failure mode, and another bill, in exchange for capabilities that
are not yet needed.

# Alternatives Considered

## Managed external queue

### Pros

- Retry, backoff, scheduling, and dead-letter handling provided.
- Sub-second latency.
- Scales beyond what polling supports.

### Cons

- Enqueue is a network call outside the transaction, reintroducing the partial-application
  hazard.
- Recovering that property requires a local outbox table, at which point most of this
  design exists anyway.
- Another vendor, secret, and cost centre before there is a user to justify it.

Decision: Rejected for now. This is the most likely successor when volume or latency
requirements change.

---

## Database scheduled jobs executing work directly

### Pros

- No application involvement.
- Scheduling built in.

### Cons

- Cannot run image processing.
- Outbound HTTP from the database is possible but awkward and hard to test.
- Handler logic lives outside the codebase, outside type checking, outside the test suite.

Decision: Rejected as the execution environment. May still be used as the trigger.

---

## Process work synchronously in the request

### Pros

- No infrastructure at all.

### Cons

- Directly violates ADR-015 and ADR-016.
- Blocks the user on work they did not ask to wait for.
- A failed notification would fail the action that caused it.

Decision: Rejected.

---

# Consequences

## Positive

- Unblocks image processing, notifications, and cleanup simultaneously.
- Jobs cannot be lost or orphaned relative to the state changes that produced them.
- Queue state is inspectable with ordinary SQL.
- No new vendor, secret, or bill.

## Negative

- Latency is bounded by drain frequency, not immediate.
- Retry and backoff are implemented rather than provided.
- Polling costs a database query per invocation whether or not work exists.
- Batch size is constrained by the function timeout.
- A stuck handler can block a job type until its attempts are exhausted.
- **The outbox property is paid for one call site at a time.** Enqueuing transactionally
  requires the domain write to already be inside a database transaction, which in this
  codebase means it must be a SQL function. At the time of implementation exactly one
  domain write qualified — `create_inspection_request_with_chat`. Every other write is an
  autocommitted PostgREST statement issued by supabase-js, and a single statement cannot
  enclose a second one. Those call sites therefore cannot enqueue transactionally as they
  stand, and each must be converted to a SQL function before it can trigger deferred work.
  The first conversion required is `updateListingStatus`, the listing approve/reject path,
  which is where the notifications slice lands first. This does not change the decision —
  the alternative is losing jobs relative to the writes that cause them — but it prices it:
  the cost of the property is a per-call-site migration, not a one-off mechanism.

---

# Non-Negotiable Constraints

- Jobs are enqueued in the same transaction as the domain write that causes them.
- Job claiming uses `FOR UPDATE SKIP LOCKED`. Overlapping invocations must not double-process.
- Every handler is idempotent. Delivery is at-least-once.
- Failed jobs after maximum attempts are retained and surfaced, never silently dropped.
- The drain route is authenticated and cannot be invoked by an anonymous caller.
- Handler failure never fails the request that enqueued the job.
- No job payload contains a secret, a token, or a signed URL.

---

# Decision Impact Assessment

## Product Impact

Enables notifications, without which an agent currently learns nothing without refreshing.
Enables image optimization, which is the platform's largest variable cost lever.

## Engineering Impact

Introduces a job table, a drain route, a handler registry, and a retry policy. Establishes
that any future deferred work is enqueued transactionally.

## Operational Impact

Queue depth and failure rate become things to watch. A drain that stops running is a
silent failure until someone notices work is not happening, so it needs monitoring.

## Risk Assessment

### Risks

- The drain stops running and nothing notices.
- A non-idempotent handler sends a notification twice.
- A slow handler consumes the batch window and starves other job types.

### Mitigations

- Alert on oldest-queued-job age, not on queue depth. Depth can be zero because nothing is
  running.
- Idempotency is a stated requirement of every handler, tested per handler.
- Batch claiming is per job type where starvation is plausible.

---

# Open Questions

- Drain frequency, which trades latency against invocation cost.
- Whether media processing shares the queue with notifications or gets its own drain, given
  their very different durations.
- Whether the scheduler is the hosting platform's cron or a database scheduled call into
  the route.

# AI Implementation Guidance

## Context

Deferred work is a row in a `jobs` table in the primary database, executed by a scheduled
call to an application route.

## Non-Negotiable Rules

- Never enqueue a job outside the transaction containing the state change that causes it.
- Never claim jobs without `FOR UPDATE SKIP LOCKED`.
- Never write a handler that breaks if executed twice.
- Never delete a permanently failed job. Retain it.
- Never place a secret, token, or signed URL in a job payload. Payloads are identifiers;
  the handler fetches what it needs.
- Never let a handler failure propagate into the request that enqueued the job.
- Never add an application-level enqueue helper. PostgREST autocommits one statement per
  request, so a TypeScript `enqueueJob()` would look transactional at the call site and
  would not be. `public.enqueue_job` is SQL precisely so it can be called from inside
  another function's transaction.

## Before Writing a Handler: the enqueue site may not exist yet

A handler is only half of a slice. The other half is the `perform public.enqueue_job(...)`
that puts the row there, and it must sit inside the same transaction as the domain write.

Check first whether the write that should trigger your handler is already a SQL function.
Usually it is not — most domain writes in this codebase are supabase-js calls, which are
autocommitted PostgREST statements and cannot enclose an enqueue. When that is the case,
converting the write into a SQL function is part of your slice, not a prerequisite someone
else has done. Budget for it.

If the conversion looks too large to take on, stop and raise it. Do not enqueue after the
write returns, and do not enqueue from a route handler, a service callback, or an `await`
that follows the commit. Each of those reintroduces the exact failure this ADR exists to
prevent: a state change that happened with no job, or a job that survived a rolled-back
state change.

## Common Mistakes

- Enqueuing after commit "because it is simpler", which loses jobs on failure.
- Assuming an enqueue site exists because a handler is easy to write. The enqueue site is
  the hard half, and for most domain writes it has to be built first.
- Claiming with a plain `SELECT` then `UPDATE`, which double-processes under concurrency.
- Treating a job as done when it is dispatched rather than when it is confirmed.
- Alerting on queue depth alone, which reads as healthy when the drain has stopped.

## Definition of Done

Jobs are enqueued transactionally, claimed without contention, retried with backoff,
retained on permanent failure, and executed by idempotent handlers in the application
runtime.
