# Architecture Decision Record (ADR) Index

## Purpose

This document serves as the authoritative index for every Architecture Decision Record (ADR) within the Ruvo Knowledge Base.

Architecture Decision Records document **why** significant technical, product, security, infrastructure, and engineering decisions were made.

While the Architecture Handbook explains **how** the system is designed, ADRs preserve the reasoning behind those decisions so future engineers can understand the context, evaluate trade-offs, and make informed changes.

This document is the primary navigation point for all ADRs.

---

# What is an ADR?

An Architecture Decision Record is a permanent record of an important architectural decision.

Every ADR answers four fundamental questions:

1. What problem existed?
2. What decision was made?
3. Why was this decision chosen?
4. What are the long-term consequences?

ADRs are immutable historical records.

If a decision changes in the future, a new ADR supersedes the previous one rather than modifying history.

---

# ADR Lifecycle

Every ADR progresses through one of the following states.

| Status | Meaning |
|---------|---------|
| Proposed | Under discussion and not yet approved. |
| Accepted | Official architecture. |
| Superseded | Replaced by a newer ADR. |
| Deprecated | No longer recommended but retained for historical reference. |
| Rejected | Considered but intentionally not adopted. |

# Writing Standards

Every ADR must include:

- Context
- Decision
- Rationale
- Alternatives Considered
- Consequences
- Constraints
- Decision Impact Assessment
- Future Considerations
- Related Documents
- AI Implementation Guidance

No ADR is considered complete without all sections.

---

# Governance

An ADR is required when a decision:

- Changes the architecture.
- Introduces new infrastructure.
- Alters security assumptions.
- Changes deployment strategy.
- Introduces a new external dependency.
- Significantly affects engineering workflow.
- Changes product architecture.

Minor implementation details do not require ADRs.

---

# Superseding an ADR

Existing ADRs are never rewritten to reflect new decisions.

Instead:

1. A new ADR is created.
2. The previous ADR is marked as **Superseded**.
3. The new ADR references the superseded ADR.
4. Historical context is preserved.

This maintains an accurate record of architectural evolution.

---

# Reading Order

New engineers should read ADRs in the following order:

1. ADR-000 (Index)
2. Platform ADRs
3. Database ADRs
4. Marketplace ADRs
5. Security ADRs
6. Infrastructure ADRs
7. Engineering ADRs

This sequence mirrors the dependency hierarchy of the system.

# AI Implementation Guidance

## Context

This document is the canonical navigation point for every architectural decision in Ruvo.

AI coding agents should consult this index before implementing significant features or proposing architectural changes.

## Non-Negotiable Rules

- Do not introduce undocumented architectural decisions.
- Do not modify accepted ADRs.
- Create a new ADR when changing architecture.
- Reference related ADRs during implementation.

## Definition of Done

Every accepted architectural decision has a corresponding ADR, appears in this index, and remains discoverable through the documented navigation structure.
