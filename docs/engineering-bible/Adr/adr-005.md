# ADR-005 — Adopt Vertical Slice Architecture

## Status

**Accepted**

---

# Context

Ruvo is expected to evolve from an MVP serving a single university town into a nationwide real estate marketplace.

Traditional layered architectures often organize projects by technical concerns:

```

controllers/
services/
repositories/
models/
utils/

```

While familiar, this approach causes related business logic to become scattered across many directories.

For example, implementing a Listing feature might require modifying:

- Controllers
- Services
- Validators
- Repositories
- DTOs
- Database Models
- Frontend Components
- API Clients

The feature becomes fragmented.

As Ruvo grows, this fragmentation increases development time, onboarding complexity, and the likelihood of inconsistent business rules.

The project requires an architecture that groups software by business capability rather than technical layer.

---

# Decision

Ruvo will adopt **Vertical Slice Architecture** as its primary application architecture.

Every feature is treated as an independent slice that contains everything required to implement that feature.

Each slice owns:

- Database interactions
- Business rules
- API handlers
- Validation
- UI components
- Tests
- Documentation

Slices communicate through well-defined interfaces rather than shared implementation details.

---

# Architectural Principles

## Business Before Technology

Directories represent business capabilities.

Examples:

```

Listings

Search

Verification

Messaging

Subscriptions

Notifications

Admin

```

Not:

```

Controllers

Services

Repositories

Helpers

```

---

## High Cohesion

Everything required for Listings lives inside the Listings slice.

Everything required for Messaging lives inside Messaging.

Business logic remains close together.

---

## Low Coupling

Slices should not directly depend upon internal implementation details of other slices.

Communication occurs through:

- Public interfaces
- Events
- Shared contracts

Never through private implementation.

---

## Independent Evolution

Each slice should evolve independently.

Adding Messaging should not require modifying Listings.

Changing Verification should not affect Payments.

---

# Why Vertical Slices?

## 1. Faster Development

An engineer implementing Listings rarely needs to leave the Listings folder.

Context switching is reduced.

---

## 2. Easier AI Assistance

AI coding agents perform significantly better when all relevant code exists in one location.

Instead of searching across dozens of folders, an AI agent can load a single feature directory and understand:

- API
- UI
- Validation
- Types
- Business rules

This dramatically improves implementation quality.

---

## 3. Better Maintainability

Business logic remains together.

Changes affect fewer files.

Refactoring becomes safer.

---

## 4. Better Testing

Each slice owns its tests.

Testing becomes feature-oriented instead of layer-oriented.

---

## 5. Better Ownership

Future engineering teams can assign ownership by feature instead of technical layer.

---

# Alternatives Considered

## Layered Architecture

### Pros

- Familiar.
- Common.
- Easy to teach.

### Cons

- Business logic becomes fragmented.
- Large cross-directory changes.
- Difficult onboarding.
- Poor AI context locality.

**Decision:** Rejected.

---

## Domain-Driven Design (Full DDD)

### Pros

- Excellent modeling.
- Rich domain language.

### Cons

- Too heavyweight for Ruvo's current team size.
- Higher implementation complexity.
- Longer onboarding.

**Decision:** Domain concepts adopted, full tactical DDD deferred.

---

## Microservices

### Pros

- Independent deployment.
- Scalability.

### Cons

- Operational complexity.
- Network overhead.
- Premature for MVP.

**Decision:** Rejected.

---

# Consequences

## Positive

- High cohesion.
- Low coupling.
- Better onboarding.
- Better AI compatibility.
- Easier testing.
- Easier maintenance.
- Faster feature delivery.

---

## Negative

- Some code duplication between slices is acceptable.
- Shared abstractions must be introduced carefully.
- Developers must resist creating large "shared" utility libraries.

---

# Non-Negotiable Constraints

- Every new feature belongs to a slice.
- Shared code must justify its existence.
- Business rules remain inside the owning slice.
- Cross-slice communication occurs only through public contracts.
- No "miscellaneous" folders.

---

# Decision Impact Assessment

## Product Impact

Allows rapid iteration while keeping business rules consistent as the marketplace grows.

---

## Engineering Impact

Reduces coupling, improves onboarding, and enables parallel feature development.

---

## Operational Impact

Simplifies debugging because failures are usually isolated to a feature slice.

---

## Risk Assessment

### Risks

- Excessive duplication.
- Overuse of shared libraries.
- Feature boundaries becoming unclear.

### Mitigations

- Regular architecture reviews.
- ADRs for new shared abstractions.
- Maintain strict feature ownership.

---

# Future Considerations

Future slices may include:

- Recommendations
- Analytics
- Mortgage Marketplace
- AI Search
- Land Marketplace

These should integrate as independent slices without disrupting existing features.

# AI Implementation Guidance

## Context

Vertical Slice Architecture is the primary organizational principle for the Ruvo codebase.

Every implementation should begin by identifying the owning feature slice.

## Non-Negotiable Rules

- Organize code by business capability.
- Keep business rules within the owning slice.
- Avoid cross-slice dependencies.
- Prefer explicit interfaces.
- Introduce shared code only after repeated, proven duplication.

## Common Mistakes

- Creating large global utility folders.
- Splitting one feature across unrelated directories.
- Moving business logic into generic helper modules.
- Building technical layers instead of business slices.

## Definition of Done

A new feature can be developed, tested, reviewed, and understood primarily within its own feature directory without requiring widespread changes across the codebase.
